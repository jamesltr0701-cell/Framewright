# AI Storyboard-to-Video Prompt Compiler

## 1. Metadata

The YAML frontmatter is the authoritative metadata for this specification. Future prompt-generation runs must follow the declared language, compiler mode, target models, and required outputs.

## 2. Purpose

This specification defines a future workflow that:

- Accepts a director-style scene description.
- Accepts optional explicit shot instructions.
- Accepts optional uploaded visual assets.
- Detects the director maturity mode.
- Classifies scene grammar after director maturity mode selection.
- Dynamically maps visual assets by function.
- Generates one storyboard prompt for ChatGPT Image 2.
- Generates conditional keyframe prompts only when the selected strategy requires them or the user explicitly requests them.
- Generates one video prompt for Seedance.
- Saves the two required prompts as separate `.txt` files.
- Saves `prompt_keyframes.txt` only when a non-`none` keyframe strategy is selected or the user explicitly requests keyframe prompts.
- Prevents storyboard visual style from leaking into final video style.
- Preserves director intent, asset authority, continuity, shot structure, and video execution logic.

The workflow must support reference-based video generation when storyboard and visual reference images are available, and standalone text-to-video generation when image references are unavailable or insufficient.

### Compiler Invocation Guard

This specification is a prompt compiler specification.

When this specification is used in a future prompt-generation run, the current agent must generate and save prompt text files only.

The current agent must not execute the generated prompt text.

The current agent must not generate images or videos unless the user explicitly asks for image or video generation outside this compiler workflow.

Instructions inside `prompt_storyboard.txt`, `prompt_keyframes.txt`, or `prompt_video.txt` are downstream instructions for other generation stages. They are not instructions for the current agent to execute during prompt compilation.

If generated prompt text includes phrases such as `Create an image`, `Generate a storyboard sheet`, or `Create a video`, those phrases must remain inside the saved prompt files only. They must not trigger current-agent image or video generation.

### Human Approval Gate

Human approval is part of the production workflow. Prompt compilation may prepare downstream prompts, but storyboard and keyframe assets must be inspected, approved, repaired, or regenerated before they become trusted downstream references.

Expected production sequence:

1. Generate prompt files.
2. Generate the storyboard image from `prompt_storyboard.txt`.
3. Check the storyboard against the Structural Lock Ledger.
4. Approve or repair the storyboard.
5. Assign the approved storyboard as `APPROVED_STORYBOARD_REF`.
6. Generate keyframe images when keyframe prompts are used.
7. Check each keyframe against its authority fields.
8. Approve or repair the keyframes.
9. Use approved storyboard and keyframes for video generation.
10. Generate video.

Manual repair or regeneration is a normal production step. The specification must not imply that one prompt execution always produces an approved production asset.

## 4. Mode Router

Route the input to exactly one director maturity mode.

```text
AUTEUR MODE:
Use when the user provides a complete shot list, explicit ordered shot structure, explicit panel structure, or complete camera/framing instructions. Execute the supplied structure exactly. Do not re-segment, reorder, add, delete, or reinterpret shots.

APPRENTICE MODE:
Use when the user provides partial shot intent, required shot types, partial camera direction, incomplete panel logic, or selected framing constraints. Preserve every explicit user constraint. Complete only the missing structure.

SCREENWRITER MODE:
Use when the user provides only a scene idea, script fragment, action flow, emotional situation, or visual description without explicit shot structure. Infer shot structure from narrative, visible behavior, geography, action, and continuity needs.
```

Routing rules:

- Route once before normalization or prompt generation.
- Do not re-route downstream.
- Treat numbered shot entries, `Shot 1`, `Shot 01`, `CU`, `MS`, `WS`, close-up, medium shot, wide shot, tracking, pan, tilt, dolly, crane, static camera, handheld, locked-off, insert, reaction shot, POV, master shot, or explicit camera movement as structural evidence only when they function as shot instructions.
- Do not classify input as AUTEUR MODE only because it uses the word `scene` in ordinary prose.
- If the input includes both scene prose and explicit shot instructions, choose AUTEUR MODE or APPRENTICE MODE according to shot completeness.
- Print the selected mode as the first line of both generated text files using exactly one of:

  - `[MODE: AUTEUR]`
  - `[MODE: APPRENTICE]`
  - `[MODE: SCREENWRITER]`

Keyframe composition authority must respect the selected mode:

- In AUTEUR MODE, user-specified shot structure remains authoritative. Strong keyframe composition authority is allowed only when the keyframe matches the specified shot.
- In APPRENTICE MODE, keyframes may have partial composition authority for user-specified elements; compiler-inferred elements remain flexible.
- In SCREENWRITER MODE, keyframes default to loose composition authority unless intentionally generated for one specific shot, insert, ECU, or critical composition proof.
- Composition authority must never silently override the Mode Router.

## 5. Scene Grammar Router

Select the scene grammar after selecting the director maturity mode. The director maturity mode determines how much shot structure the user controls. Scene grammar determines pacing language, panel density, feedback intensity, camera execution style, and video execution language.

Use this analysis schema:

```yaml
scene_grammar_analysis:
  scene_grammar_type:
  continuous_take:
  camera_execution:
  pacing_profile:
  feedback_intensity:
  motion_intensity:
  notes:
```

Allowed values:

```yaml
scene_grammar_type:
  - kinetic_scene
  - observational_scene
  - conversational_scene

continuous_take:
  - true
  - false

camera_execution:
  - locked_off
  - handheld_follow
  - slow_track
  - dolly_push
  - lateral_track
  - orbit
  - static_coverage
  - mixed_coverage
  - director_specified

feedback_intensity:
  - low
  - medium
  - high

motion_intensity:
  - minimal
  - soft
  - moderate
  - aggressive
```

Grammar definitions:

```text
kinetic_scene:
Use for scenes driven by physical motion, combat, chase, escape, panic movement, slapstick, mechanical struggle, physical procedure with visible resistance, or fast cause-and-effect action. A kinetic scene can be soft, moderate, or aggressive. It is not always violent or high-impact.

observational_scene:
Use for scenes driven by stillness, duration, atmosphere, solitary behavior, careful procedure, object handling, quiet emotional observation, negative space, micro-movement, or slow spatial attention.

conversational_scene:
Use for scenes driven by dialogue, silence between characters, eye-line exchange, reaction timing, blocking distance, social pressure, refusal to answer, emotional negotiation, or relationship tension.
```

Classification rules:

- Select the scene grammar after selecting AUTEUR MODE, APPRENTICE MODE, or SCREENWRITER MODE.
- Scene grammar must not change the selected director maturity mode.
- Scene grammar must not change explicit shot count, shot order, framing, camera movement, or shot scale supplied by the director.
- If multiple grammar types are present, choose the dominant grammar that controls the main scene experience.
- If a scene contains physical motion but the emotional focus is quiet observation, choose `observational_scene` and set `motion_intensity` to `soft` or `minimal`.
- If a scene contains dialogue while characters are walking or moving, choose `conversational_scene` when the dialogue and reactions are the main event.
- If a scene contains a following one-take camera move, do not automatically classify it as `observational_scene`. Set `continuous_take` to `true` and classify the grammar by the scene's main dramatic engine.
- A following one-take chase or fight is `kinetic_scene` with `continuous_take` set to `true`.
- A following one-take walk-and-talk is `conversational_scene` with `continuous_take` set to `true`.
- A following one-take silent walk through a room, hallway, or landscape is `observational_scene` with `continuous_take` set to `true`.
- Classify scene grammar primarily from director text, explicit shot structure, action logic, dramatic engine, and the central readable event.
- Visual asset style, color, medium, lighting, atmosphere, or emotional finish must not change the scene grammar unless the user explicitly states that the asset mood should determine pacing or scene behavior.
- Visual assets may influence final video appearance through the Asset Authority Map, but they must not replace director action logic when selecting scene grammar.
- If the scene's central readable event is a physical obstacle, mechanical struggle, stuck/free state, chase, fall, impact, object movement, or visible physical resistance, prefer `kinetic_scene` with `motion_intensity` set to `soft`, `moderate`, or `aggressive` according to tone.
- If a physical event is secondary and the main experience is stillness, care, waiting, emotional observation, or careful attention, choose `observational_scene`.
- A gentle domestic mechanical problem may be `kinetic_scene` with `motion_intensity: soft` and `feedback_intensity: low`.
- Do not convert a soft kinetic scene into `observational_scene` only because the visual assets have a warm, painterly, quiet, or gentle style.

Control rules:

- Scene grammar controls pacing language, panel density, feedback intensity, rhythm marker choice, physical verb choice, audio design language, and the level of environmental or mechanical response.
- Scene grammar does not control final video style.
- Scene grammar does not override the Asset Authority Map.
- Scene grammar does not override the Style Firewall.
- Scene grammar does not authorize storyboard rendering style to leak into final video style.

## 6. Asset Authority Map

Create an internal asset authority map before writing either prompt file. Assign every uploaded asset one or more of these roles:

```yaml
asset_roles:
  - storyboard_structural_reference
  - keyframe_visual_reference
  - character_reference
  - creature_reference
  - subject_reference
  - prop_or_object_reference
  - mechanical_subject_reference
  - vehicle_reference
  - environment_layout_reference
  - style_reference
  - lighting_reference
  - texture_reference
  - atmosphere_reference
  - scale_reference
  - unused_or_ambiguous_reference
```

Role definitions:

```text
storyboard_structural_reference:
A generated or supplied storyboard image used only for shot order, framing, staging, camera placement, action beats, screen direction, and spatial continuity.

keyframe_visual_reference:
A final-style still image used for visual style, lighting, texture, surface fidelity, subject finish, scale, orientation, shot-specific composition, and material treatment within its assigned coverage.

character_reference:
A reference used for character identity, face, body proportions, silhouette, wardrobe, hair, posture, expression range, movement quality, and character-specific rendering finish.

creature_reference:
A reference used for creature identity, anatomy, silhouette, surface, motion limits, expression limits, scale, and rendering finish.

subject_reference:
A general reference for any primary non-character subject that does not fit a more specific role.

prop_or_object_reference:
A reference used for object shape, size, state, material, surface, functional limits, texture, and interaction behavior.

mechanical_subject_reference:
A reference used for machines, robots, devices, tools, vehicles, or any subject with mechanical or functional structure, including design, moving parts, facing surfaces, screen or indicator behavior when present, material boundaries, and behavior limits.

vehicle_reference:
A reference used for vehicle design, scale, orientation, functional surfaces, material treatment, and motion constraints.

environment_layout_reference:
A reference used for location layout, architecture, entrances, exits, surfaces, furniture, set anchors, spatial proportions, and screen direction.

style_reference:
A reference used for final visual style, medium, finish, texture behavior, color behavior, line quality, lighting behavior, and aesthetic treatment.

lighting_reference:
A reference used for lighting behavior, source direction, softness, contrast, color temperature, and exposure mood.

texture_reference:
A reference used for material grain, surface behavior, brush texture, fabric texture, organic texture, mechanical texture, environmental texture, or atmospheric texture.

atmosphere_reference:
A reference used for weather, haze, mist, dust, steam, air density, reflections, environmental mood, or ambient conditions.

scale_reference:
A reference used for relative size relationships between subjects, props, objects, architecture, and environment anchors.

unused_or_ambiguous_reference:
A reference that cannot be safely assigned or should not influence generation.
```

Asset authority rules:

- Do not hardcode `@image1` as storyboard, `@image2` as character, or any fixed asset order.
- The future workflow has two phases:

  1. Generate `prompt_storyboard.txt`.
  2. Use the resulting storyboard image as a possible structural reference when generating or using `prompt_video.txt`.

- If a storyboard image has already been generated from `prompt_storyboard.txt`, assign that storyboard image the role `storyboard_structural_reference`.
- In `prompt_video.txt`, include a prominent `REFERENCE REGISTRY` near the top.
- The `REFERENCE REGISTRY` must include the storyboard reference slot and must state each available asset handle, its assigned role, and its authority.
- If no image references are available, the video prompt must remain usable as a standalone text-to-video prompt.
- Do not rely exclusively on image references for subject, action, environment, camera, or continuity.
- Restate essential subject, action, environment, camera, continuity, and style information in text.
- All non-storyboard visual assets contribute to final video aesthetic continuity unless the user explicitly excludes them.
- Dedicated style reference assets have highest authority for overall final video style.
- Character reference assets contribute character identity and character-specific rendering style, including line quality, stylization boundary, facial finish, fabric finish, hair treatment, color behavior, texture behavior, and visible material treatment for that character.
- Creature, vehicle, robot, prop, tool, device, object, or product reference assets contribute design, scale, material boundaries, mechanical or functional design when relevant, object-specific color behavior, surface treatment, texture behavior, and rendering finish for those subjects.
- Environment reference assets contribute layout, lighting, atmosphere, spatial materials, color behavior, environmental texture, and overall location finish.
- Lighting, texture, and atmosphere references contribute their assigned visual properties only.
- The generated storyboard image never contributes final video style.
- If multiple non-storyboard assets have compatible visual styles, harmonize them into one coherent final video aesthetic stack.
- If non-storyboard assets conflict in style, prioritize:

  1. Explicit user instruction.
  2. Dedicated style reference.
  3. Environment reference for lighting and atmosphere.
  4. Character reference for character rendering.
  5. Object, prop, tool, device, vehicle, creature, or robot reference for that subject's rendering.

- Do not treat `character_reference` as identity-only by default. A character reference also contributes character-specific final rendering style unless the user explicitly limits it to identity only.
- Do not infer that an asset contributes only identity, layout, or geometry if it also visibly defines rendering finish, line treatment, color behavior, material texture, or stylization boundary.
- Assign generated final-style keyframe images the role `keyframe_visual_reference` and record their panel or shot coverage and visual authority.
- Keyframe references contribute final-style appearance only within their assigned coverage and never replace storyboard structural authority.
- When visual references contain distinctive surface behavior, record the authorized line quality, medium grain, wear, imperfection, texture, material finish, and stylization boundary in the asset notes.
- Do not use `robot_or_prop_reference` as a default role name.
- Do not use `R1` as a default placeholder in templates.
- Do not use mechanical-subject wording in templates unless the current input contains a mechanical subject.
- Use `MECH_1` only for mechanical subjects.
- Use `PROP_1` or `OBJECT_1` for non-mechanical props or objects.
- Use `SUBJECT_1` for a primary non-character subject when no more specific role is appropriate.
- Do not force every scene into character-plus-object language.

### Lock Source Hierarchy

```yaml
lock_source_hierarchy:
  explicit_user_lock:
    priority: highest
    meaning: directly stated by the user, explicit shot instruction, explicit scene constraint, or explicit asset instruction.
  asset_inferred_lock:
    priority: high
    meaning: inferred from clear visual asset evidence, filename, asset sheet notes, visible scale, visible orientation, visible design, or visible material state.
  action_inferred_lock:
    priority: medium
    meaning: inferred from action logic, interaction logic, eye-line logic, tool access, relationship blocking, or cause-effect readability.
  compiler_preference:
    priority: lowest
    meaning: chosen by the compiler for clarity, aesthetics, readability, or conventional staging when no stronger lock exists.
```

- Classify every relevant scale, orientation, facing, composition, object-state, shot-order, shot-size, and action-proof constraint by source.
- Explicit user locks must be preserved unless they directly conflict with a later explicit user instruction.
- Asset-inferred locks are strong but must not override explicit user locks.
- Action-inferred locks are recommended structural logic and must be labeled as inferred.
- Compiler preferences must never be presented as explicit director instructions.
- If an inferred lock may affect interpretation, make it visible for user review.
- Do not overstate inferred relationships as hard user commands or invent locks that conflict with user text or asset evidence.
- Use this wording pattern: `Source: explicit_user_lock | asset_inferred_lock | action_inferred_lock | compiler_preference`.

## 7. Continuity Firewall

The Continuity Firewall governs identity, space, props, mechanics, and style across the storyboard and video prompts.

### 7.1 Identity and Subject Continuity

- Use stable role-based IDs such as `CHARACTER_1`, `CHARACTER_2`, `SUBJECT_1`, `PROP_1`, `OBJECT_1`, `MECH_1`, `VEHICLE_1`, or `ENVIRONMENT_1` only when relevant to the input.
- Preserve character identity across all storyboard panels and video beats.
- Preserve creature identity, primary subject design, prop or object identity, mechanical subject design, and vehicle identity across storyboard panels, keyframes, and video shots when those roles are present.
- Preserve face, silhouette, wardrobe, body proportions, hair, key props, and movement quality when supported by director text or assets.
- Do not redesign, age-shift, beautify, caricature, merge, or replace characters unless explicitly requested.
- Use asset references only within their assigned authority roles.

### 7.2 Spatial and Prop Continuity

- Preserve room layout, thresholds, entrances, exits, furniture placement, screen direction, camera axis, and set anchors.
- Preserve prop state and mechanical state across panels and video beats.
- For mechanical subjects, preserve design, moving parts, functional surfaces, indicator behavior when present, material boundaries, state, resistance, and movement limitations.
- If multiple panels occur in the same location, describe them as the same layout rather than a redesigned space.
- Allowed changes must come from the director description or the shot logic.

### 7.3 Scale Continuity

- Define a Scale Contract whenever characters, creatures, vehicles, robots, props, tools, devices, objects, furniture, architecture, or environment anchors appear together.
- The Scale Contract must describe relative size relationships in text.
- Use stable comparative anchors such as head size, shoulder height, waist height, knee height, hand size, doorway height, bed height, table height, chair height, floor tile scale, object-to-body proportion, or object-to-environment proportion.
- If a subject, prop, object, or environment element has a director-specified scale, preserve it across storyboard panels and video shots.
- If a scale reference asset is provided, assign it the role `scale_reference` and record its authority inside the asset notes.
- If no scale reference asset is provided, infer a text-based Scale Contract from director text, visual assets, and spatial context.
- Do not let foreground placement, wide-angle distortion, furniture scale, environment perspective, or shot framing accidentally resize a character, creature, vehicle, robot, prop, tool, device, object, or environment anchor.
- Do not rely only on image references for scale continuity. State the key scale relationships in text.

### 7.4 Orientation, Facing, and Composition Continuity

- Define an Orientation Contract whenever a subject, object, prop, vehicle, mechanical subject, creature, character, or environment element has a meaningful front, back, side, display surface, face, sensor, door, opening, label side, functional side, interaction side, screen, window, handle, tool end, direction of travel, or facing relationship.
- The Orientation Contract must state:

  1. Which side faces the camera.
  2. Which side faces another subject.
  3. Which side faces the action.
  4. Which side must remain visible.
  5. Which side must not flip.
  6. What relationship is explicit.
  7. What relationship is inferred from action logic.

- Do not make a subject rotate toward the viewer if doing so breaks the story relationship, interaction logic, action readability, or director instruction.
- Use this principle: visible enough for the viewer, but oriented according to the scene relationship.
- If a facing relationship is explicit in the user input, preserve it.
- If a facing relationship is not explicit but is required for action readability, interaction logic, eye-line, or emotional relationship, infer the safest relationship and mark it as inferred in the prompt.
- Do not invent a facing relationship that conflicts with user intent.
- If a subject has a display, face, window, label, front side, or functional surface, preserve its orientation across storyboard panels, keyframes, and video shots unless a deliberate turn is part of the action.
- Preserve left-right orientation, screen direction, near-side or far-side interaction, tool approach side, and object-facing relationship when relevant.
- Apply the Lock Source Hierarchy to every Orientation Contract and distinguish explicit relationships from inferred staging.

### 7.5 Face-Like Surface Orientation Rule

- A face-like surface is any subject surface that a model may treat as a face, display, eye, lens, sensor, circular window, screen, dashboard, muzzle, camera, indicator, or front-facing identity surface.
- If a face-like surface has a required orientation, define it explicitly in the Orientation Contract.
- If the required orientation faces another character, subject, or action target, the surface must not rotate toward the viewer only for visual clarity.
- Apply this principle: visible enough for the viewer, but oriented according to the relationship.
- When a face-like surface must not face the viewer, specify an oblique, foreshortened, partial, side-angled, rim-visible, or three-quarter non-frontal view.
- Do not say only that the surface is visible if visibility may cause it to rotate toward camera.
- State the character, subject, action target, or camera that the surface faces.
- If orientation is inferred from action logic, label it `Source: action_inferred_lock`.

### 7.6 Style Firewall

The generated storyboard image is a structural reference only.

Storyboard rendering style must never define final video style.

Do not transfer storyboard linework, graphite marks, monochrome palette, paper texture, panel borders, labels, UI layout, unfinished construction marks, or storyboard-sheet design into the final video.

Final video style may come only from:
1. designated video style reference assets,
2. designated lighting, texture, or atmosphere reference assets,
3. assigned non-storyboard visual assets within their assigned authority,
4. explicit director text.

If no dedicated video style reference is provided, derive final video appearance only from explicit director text, character assets, environment assets, lighting assets, texture assets, and atmosphere assets.

Do not derive final video style from the storyboard sheet.

Character, creature, prop, vehicle, robot, object, and environment references must not be cleaned up into a generic default style unless the user explicitly requests that style.

Do not beautify, polish, simplify, age-shift, redesign, replace, or normalize a subject beyond the supplied reference and director instructions.

Preserve the authorized finish of each non-storyboard reference, including line imperfection, facial texture, surface irregularity, fabric softness, hair treatment, material grain, texture behavior, color behavior, non-glossy or glossy finish, and stylization boundary when visible or described.

When the final video uses a hand-drawn, watercolor, ink, painterly, graphite, clay, stop-motion, cinematic, photoreal, stylized, or other aesthetic stack, all subjects must be rendered within the same authorized stack unless a separate subject-specific style override is provided.

Do not let a character, creature, prop, vehicle, robot, object, or environment become cleaner, more generic, more anime-like, more photoreal, more polished, more symmetrical, or more beautified than the authorized references support.

When references contain distinctive texture, medium, line quality, material finish, wear, imperfection, or handmade behavior, define a Surface Fidelity Lock and preserve it across keyframes and video shots.

## 8. Storyboard Prompt Rules for ChatGPT Image 2

`prompt_storyboard.txt` must instruct ChatGPT Image 2 to generate a storyboard sheet image, not a final video.

- Use the selected mode as the first line.
- Generate a compact storyboard sheet prompt.
- Optimize the storyboard sheet for readable production planning.
- Use the minimum panel count required for clear cause and effect.
- In AUTEUR MODE, preserve exact shot count, shot order, framing, camera movement, and shot scale.
- In APPRENTICE MODE, preserve all explicit shot instructions and complete only missing structure.
- In SCREENWRITER MODE, infer panel count and camera structure from action, geography, visible behavior, and continuity needs.
- Each panel must represent one frozen instant.
- Each panel must contain one dominant visual beat.
- Do not describe temporal sequences inside a single panel.
- Do not use sequential wording inside panel descriptions, including temporal use of `then`, `after`, `before`, `first`, `next`, `later`, `gradually`, `continues`, or `remains ... then`.
- If a listed word is used spatially rather than temporally, rewrite it to avoid ambiguity.
- Use visible behavior instead of abstract emotion.
- Convert psychology into posture, spacing, eye-line, hand tension, blocking, object state, or camera distance.
- Do not render detailed facial anatomy, finished facial illustration, beauty rendering, or character-design detail inside storyboard panels.
- However, when an emotional reaction is the main visual beat, allow minimal expression marks required for readability, such as eye-line direction, brow angle, head tilt, shoulder release, mouth curve, or a small smile.
- Minimal expression marks must remain schematic and production-board level. They must not become finished facial rendering.
- Translate director phrases such as `behind camera`, `offscreen behind camera`, `from behind the camera`, or `toward the camera-side source` into visible composition and blocking language.
- Do not rely on abstract camera-position wording when writing panel descriptions.
- Use visible terms such as `near-camera foreground edge`, `camera-side doorway`, `camera-side threshold`, `foreground entrance`, `walking away into depth`, `looking back toward the camera-side source`, or `eye-line aimed toward the near-camera offscreen area`.
- Preserve the director's intended geography, but express it as a visible frame relationship.
- Panel interiors must contain only visual staging: characters, environment, props, poses, effects, framing, and composition.
- Panel interiors must not contain text, arrows, captions, speech bubbles, subtitles, labels, diagrams, UI, timing marks, camera rigs, technical overlays, duplicate bodies, or ghost poses.
- Panel numbers, camera notes, shot names, and other metadata must stay outside panel image areas.
- Default storyboard panel rendering is production-board line art: open-outline silhouettes, thin graphite linework, simplified forms, broad negative space, paper-white field, sparse construction marks, no filled regions, no rendered lighting, no gradients, no material finish, no painterly texture, no photorealistic detail.
- Do not let the storyboard become finished manga line art, final illustration, concept art, or video-style artwork. Preserve structural readability over beauty inside panels.
- Visual assets may control storyboard identity, geometry, proportions, prop shape, and environment layout.
- Visual assets must not transfer color, lighting, texture, painterly finish, material finish, or final-video style into storyboard panel interiors unless explicitly requested.
- The storyboard prompt must not include a Director Strip.
- The storyboard prompt must include the selected scene grammar in a compact text field outside the panel image areas.
- Scene grammar may influence panel density and shot sampling, but it must not override explicit director shot instructions.
- For `kinetic_scene`, use enough panels to make physical cause-and-effect readable. Prioritize contact state, directional force, body position, object state, impact timing, mechanical resistance, and visible result.
- For `observational_scene`, use fewer panels unless the director requests more. Prioritize negative space, stillness, slow body movement, spatial duration, object state, environmental texture, light behavior, and small visible changes.
- For `conversational_scene`, prioritize eye-line, blocking distance, body orientation, pauses, reaction timing, hand behavior, seated or standing position, and spatial relationship between speakers.
- For `continuous_take: true`, treat panels as sampled phases of one uninterrupted camera path, not separate cuts, unless the director explicitly requests otherwise.
- For `continuous_take: true`, state the continuous camera path in `CAMERA CONTINUITY`.

### Board Presentation Shell

- The storyboard sheet must be presentable as a clean production board, not a rough dump of panels.
- Storyboard panel interiors must remain structural and de-stylized.
- Storyboard sheet exterior may use restrained presentation design.
- Presentation design may include a clean masthead, project card, thin border rules, consistent margins, even gutters, compact panel header strips, subtle non-storytelling graphic accents, and clear layout hierarchy.
- Presentation design must stay outside panel image areas.
- Presentation design must not add storytelling content, extra characters, decorative illustrations, false props, icons, logos, UI, arrows, labels inside panels, or final-video style.
- Do not increase facial detail, clothing detail, background detail, rendering finish, shading, color, painterly treatment, or illustration completeness inside panel interiors to make the board look polished.
- Sheet polish must come from layout, spacing, hierarchy, headers, margins, gutters, and exterior graphic restraint, not from finished illustration inside panels.

### Panel Header Strip

- Every storyboard panel must have a compact panel header placed outside the panel image area.
- Use this exact header format unless the user requests another format: `P## / shot size / beat name`.
- Panel headers must be short, readable, and consistent.
- Panel headers must not appear inside panel interiors.
- Panel headers must not replace visual storytelling inside the panel.
- Panel order must still be enforced by grid order, `P##` order, and prompt text, not by header text alone.
- For scenes with more than six panels, panel headers are required for order clarity.
- For scenes with three or fewer panels, panel headers are still required unless the user explicitly requests no headers.

### Insert and ECU Crop Fidelity

- If a storyboard panel is labeled `insert`, `detail`, `CU`, `ECU`, `extreme close-up`, `macro`, or equivalent, the panel must crop tightly around the required visual information.
- Do not automatically widen an insert or ECU panel into a character bust shot, medium shot, room view, or general emotional close-up.
- For procedure, contact, object state, tool use, display state, texture detail, or physical resistance, the crop must prioritize the relevant hands, tools, surfaces, contact points, object state, or visual evidence.
- Only include face, torso, room background, or wider context in an insert or ECU if the director explicitly requests it or if the detail cannot read without that context.
- If the shot label and the description conflict, preserve the director's explicit intent and clarify the crop in prompt text.
- For storyboard sheets, insert and ECU panels must remain single frozen instants, not miniature temporal sequences.

### Storyboard State-Color Exception

- Storyboard panel interiors are monochrome or de-stylized by default.
- A sparse schematic state-color marker is allowed only when color is essential to understanding a state, signal, status, warning, screen, light, material change, injury, magical effect, or other critical visual condition.
- State-color markers must be minimal.
- State-color markers must not create final illustration style.
- State-color markers must not become lighting, palette, atmosphere, texture, or final video style authority.
- State-color markers must not override the Style Firewall.
- If color is not essential to state readability, express the state through shape, position, contrast, line marks, or composition instead.
- If a state-color marker is used in the storyboard prompt, explicitly state that it is schematic and structural only.

### Structural Lock Ledger

- Include a Structural Lock Ledger whenever important scale, orientation, facing, composition, shot-order, action-proof, ECU, insert, object-state, character-position, or spatial-continuity constraints exist.
- The ledger is a concise text-only planning block outside storyboard panel image areas.
- Classify every ledger item with the Lock Source Hierarchy.
- Distinguish hard locks, inferred locks, compiler preferences, and user-check items.
- The ledger must not add story events, appear inside panels, or replace normal storyboard instructions.
- Include face-like surface direction in the ledger when relevant.

### Storyboard Structural Compliance Gate

- Check the generated storyboard image before using it as structural authority for keyframes or video.
- The compliance gate evaluates structural facts, not final beauty, rendering polish, or final style unless those affect readability.
- Check panel order, shot count, structurally important shot scale, identity, relative scale, orientation, facing, face-like surface direction, camera axis, screen direction, object state, action proof, reaction target, insert or ECU crop, anatomy, duplicate limbs or subjects, extra props or tools, spatial continuity, and storyboard purity.
- A storyboard passes only when essential structural locks are readable.
- Hard-lock failures require repair or regeneration.
- Inferred-lock failures must be surfaced for user review unless they break action readability.
- Compiler-preference failures may be accepted by the user.
- Do not use an unapproved storyboard as strong downstream structure authority.
- Keyframe prompts compiled before storyboard generation must require `APPROVED_STORYBOARD_REF` before execution.
- The compliance gate does not block prompt compilation; it blocks trusted downstream execution until approval or repair.

### Repair-Friendly Storyboard Workflow

- If the storyboard fails the Structural Compliance Gate, repair or regenerate it before downstream use.
- Repair instructions must be short, targeted, structural, and limited to failed facts.
- Do not use repair prompts to improve final style or repaint the board as final art.
- Repairs may correct scale, orientation, facing, face-like surface direction, anatomy, duplicate subjects, ECU or insert crop, panel order, object state, action proof, reaction target, extra props, or storyboard purity.
- Preserve every passing structural lock, subject identity, story event, and shot order.
- After repair, the repaired image becomes a candidate for `APPROVED_STORYBOARD_REF`.
- The user may approve, reject, repair, or regenerate the storyboard. Manual repair is a normal production step.

## 10. Video Prompt Rules for Seedance

`prompt_video.txt` must support two workflows:

```text
reference_based_workflow:
Use when storyboard image and visual assets are available.

standalone_t2v_workflow:
Use when image references are unavailable or insufficient.
```

Apply these rules:

- The standard workflow for this specification is storyboard-first.
- `prompt_storyboard.txt` is expected to generate an upstream storyboard image.
- `prompt_video.txt` must be reference-ready for that generated storyboard image.
- Because `prompt_video.txt` may be generated before the storyboard image receives a runtime image handle, the video prompt must include a storyboard reference slot rather than assuming a fixed handle such as `@image1`.
- When the generated storyboard image is attached during video generation, assign it the role `storyboard_structural_reference`.
- The storyboard reference controls only shot order, framing, camera placement, staging, action beats, screen direction, spatial continuity, and panel-to-shot structure.
- The video prompt must remain self-contained enough for standalone text-to-video generation if the storyboard image is unavailable, not attached, or ignored by the video model.
- Self-contained means that subject, action, environment, camera logic, continuity, visual style, and temporal execution must all be stated in text.
- Do not write the video prompt in a way that depends exclusively on the storyboard reference.
- Do not phrase the storyboard reference as an optional creative influence. It is the standard structural authority in the reference-based workflow.
- Do not hardcode the storyboard reference as `@image1`. Use `APPROVED_STORYBOARD_REF` as an approval-required alias or assign the approved runtime handle when available.
- Do not execute keyframe or video prompts with strong storyboard authority until the Structural Compliance Gate is passed and the user approves the storyboard.
- Use the selected mode as the first line.
- Always include a `REFERENCE REGISTRY`; include non-storyboard runtime handle entries only when those assets are available.
- The generated storyboard image is used only as structural authority.
- Storyboard structural authority includes panel order, shot structure, framing, camera placement, staging, action beats, screen direction, and spatial continuity.
- The storyboard image must not control final video style.
- The video prompt must explicitly include Style Firewall instructions.
- The video prompt must remain self-contained enough for text-to-video generation.
- Restate subject, action, environment, camera behavior, continuity, and visual style in text even when image references are available.
- Final video style must come only from explicit director text and assigned non-storyboard visual assets within their authority.
- Use panel or shot execution beats that match the storyboard structure.
- In AUTEUR MODE, preserve the director-provided shot structure exactly.
- In APPRENTICE MODE, preserve explicit shot intent and complete missing motion execution.
- In SCREENWRITER MODE, follow compiler-generated storyboard panel order.
- Add a `SHOT PLAN`.
- The Shot Plan replaces the Director Strip.
- The Shot Plan must be text-only and must not be part of the storyboard sheet.
- Each video beat must include rhythm, performance pressure, subject action, environmental feedback, mechanical feedback when relevant, and audio design notes.
- Do not use unsupported large environmental reactions.
- Use the minimum physical feedback needed to ground the action.
- Couple character action with environment or mechanical response when relevant.
- Mechanical feedback may include vibration, resistance, sliding, scraping, blocked movement, motor hesitation, light response, screen flicker, track friction, small impacts, or object recoil.
- Environmental feedback may include air movement, water movement, fabric movement, dust, mist, steam, leaves, reflections, shadows, surface contact, or nearby loose objects.
- Audio design notes are planning references only. Do not claim that Seedance will generate audio unless the workflow explicitly supports audio generation.
- The video prompt should include diegetic ambience, foley, impacts, mechanical texture, silence, or sound surges when relevant.
- Avoid restating storyboard sheet UI, panel borders, sheet labels, or storyboard rendering style as video content.
- Do not instruct the model to render the storyboard sheet.
- The video prompt must include the selected scene grammar.
- Scene grammar controls video execution language.
- For `kinetic_scene`, use action-driven rhythm markers, physical verbs, environmental feedback, mechanical feedback when relevant, contact timing, momentum shifts, impact behavior, and energetic audio design notes. Feedback intensity may be low, medium, or high depending on the scene.
- For `observational_scene`, use restrained rhythm markers, quiet action verbs, micro-movement, negative space, ambient continuity, subtle environmental changes, room tone, silence, light behavior, and minimal physical feedback.
- For `conversational_scene`, use reaction-based rhythm markers, eye-line shifts, pauses, breath, posture changes, blocking distance, hand tension, offscreen sound, room tone, and conversational pressure.
- For `continuous_take: true`, the video prompt must describe one uninterrupted camera path. Panel or shot entries represent phases of the same take, not separate cuts, unless the director explicitly requests otherwise.
- For `continuous_take: false`, panel or shot entries may represent separate cuts, according to the selected mode and director instructions.
- Every video execution beat must include at least one appropriate feedback channel:

  1. performance feedback,
  2. environmental feedback,
  3. mechanical feedback when relevant,
  4. acoustic feedback.

- Do not invent environmental feedback when the scene grammar does not need it.
- Do not invent mechanical feedback when no robot, machine, vehicle, tool, device, or mechanical prop is present.
- If environmental or mechanical feedback is not relevant for a beat, write `none needed` or omit the channel, according to the prompt format being used.
- Performance pressure must match the selected scene grammar, feedback intensity, and motion intensity.
- For `motion_intensity: minimal`, use low performance pressure unless the director explicitly requests tension.
- For `motion_intensity: soft`, use low or medium performance pressure by default.
- For soft kinetic scenes, do not mark an entire beat as high pressure unless the central action truly requires it.
- For soft kinetic scenes with a brief resistance spike, write `medium pressure with a brief high-resistance moment` rather than labeling the whole beat as high pressure.
- For `motion_intensity: aggressive`, high performance pressure is allowed when supported by the director's action logic.

- Do not force high-intensity environmental feedback into `observational_scene` or `conversational_scene` unless the director explicitly requests it.
- Do not use action-choreography language for `observational_scene` or `conversational_scene` unless the director explicitly requests high-energy action.

### Reference Registry

- The video prompt must place all runtime image handles in a prominent `REFERENCE REGISTRY` near the top of the prompt.
- Raw image handles such as `@image1`, `@image2`, or actual runtime asset handles must appear only in the `REFERENCE REGISTRY`, unless the user explicitly requests inline handle repetition.
- After the `REFERENCE REGISTRY`, use stable symbolic aliases such as `APPROVED_STORYBOARD_REF`, `CHARACTER_1_REF`, `CHARACTER_2_REF`, `CREATURE_1_REF`, `SUBJECT_1_REF`, `SUBJECT_2_REF`, `PROP_1_REF`, `OBJECT_1_REF`, `MECH_1_REF`, `VEHICLE_1_REF`, `ENV_REF`, `STYLE_REF`, or `SCALE_REF` instead of repeating raw image handles throughout the prompt.
- Use only aliases that are relevant to the current project.
- The registry must be easy for the user to audit before video generation.
- The registry must include every required uploaded reference, its assigned role, and its authority.
- If a required reference is missing, state that in the final Codex response instead of hiding the issue inside the prompt.

### Aesthetic Reference Stack

- The video prompt must include an `AESTHETIC REFERENCE STACK`.
- The Aesthetic Reference Stack defines which non-storyboard assets control final video appearance.
- The generated storyboard image is excluded from the Aesthetic Reference Stack.
- All non-storyboard visual assets contribute to final video aesthetic continuity unless explicitly excluded by the user.
- Character references contribute character rendering style for their characters.
- Creature, vehicle, robot, prop, tool, device, object, or product references contribute rendering style and material treatment for those subjects.
- Environment references contribute lighting, atmosphere, spatial material, environmental finish, and location style.
- Dedicated style references control the broad final video style if provided.
- The video prompt must harmonize the Aesthetic Reference Stack into one coherent final visual treatment.
- Do not let any subject become cleaner, more generic, more anime-like, more photoreal, more polished, or more beautified than the authorized references or aesthetic stack support.

### Scale Contract

- The video prompt must include a `SCALE CONTRACT` whenever characters, creatures, vehicles, robots, props, tools, devices, objects, furniture, architecture, or environment anchors appear together.
- The Scale Contract must state relative proportions clearly.
- The Scale Contract must not rely only on image references.
- Use comparative language based on the actual scene, such as subject-to-body scale, subject-to-hand scale, subject-to-head scale, subject-to-furniture scale, subject-to-doorway scale, subject-to-floor scale, or subject-to-environment scale.
- If a dedicated scale reference is available, include it in the Reference Registry and give it explicit scale authority.
- If no scale reference is available, infer scale from director text, asset context, and spatial logic.
- The Negative Prompt must block accidental resizing of characters, creatures, vehicles, robots, props, tools, devices, objects, and environment anchors when relevant.

### Editing Plan and Rhythm Shape

- Unless the director explicitly requests another transition style, use clean hard cuts between separate shots.
- Do not use dissolve, crossfade, ghost overlap, blended transition, or morphing transition unless explicitly requested.
- If `continuous_take: true`, do not use cuts unless explicitly requested.
- If `continuous_take: false`, use hard cuts by default.
- The video prompt must include a `RHYTHM SHAPE` that describes relative shot duration and energy.
- Use relative duration language rather than exact timestamps unless the user explicitly provides timing.
- Avoid flattening every shot into equal duration and equal energy.
- AUTEUR MODE shot order and shot count remain authoritative, but rhythm shape may define relative emphasis within that structure.

### Ambient Life Layer

- The video prompt must include subtle ambient life motion when appropriate.
- Ambient life motion is background or environmental micro-motion that keeps a quiet or low-motion scene alive without adding story events.
- For `observational_scene` and soft `kinetic_scene`, include one or two subtle ambient life motions unless the director explicitly requests total stillness.
- Ambient life may include low-intensity motion in fabric, plants, steam, dust, reflections, water, light, shadow, air, distant exterior glow, small background objects, or room-tone behavior.
- Ambient life must be low intensity.
- Ambient life must not distract from the subject.
- Ambient life must not create new plot events.
- Ambient life is different from environmental feedback. Environmental feedback is caused by subject action. Ambient life exists independently within the scene atmosphere.

### Execution Precision Layer

- The video prompt must preserve reaction target relationships.
- If a reaction shot depends on a character, creature, vehicle, robot, prop, tool, device, object, or offscreen source, state the target clearly.
- When possible, keep part of the reaction target visible in the foreground, background, reflection, edge of frame, or spatial anchor.
- If the reaction target must remain offscreen, state the exact offscreen eye-line anchor.
- For small physical actions, mechanical struggle, object handling, procedural action, contact, resistance, or object state change, write a micro-action arc.
- A micro-action arc describes:

  1. Attempt.
  2. Resistance.
  3. Visible result.

- Do not exaggerate soft kinetic micro-action into violent impact unless the director requests it.
- Do not leave a physical struggle, mechanical struggle, or procedural action as a static object state if the beat requires attempted motion.

### Performance Micro-Life

- For held human, creature, or character shots, include natural performance micro-life when appropriate.
- Performance micro-life may include a single blink, breath, tiny eye-line adjustment, small swallow, slight shoulder release, subtle hand tension change, small posture settling, or brief facial stillness change.
- For `observational_scene`, `conversational_scene`, and soft `kinetic_scene`, performance micro-life is especially important when the shot is quiet, low-motion, or held for a long duration.
- Do not force visible blinking into every shot.
- Do not overuse blinking.
- Do not add blinking during a critical fixed stare, impact moment, or exact expression hold unless it supports the intended performance.
- Performance micro-life must be subtle and must not create new story events.
- Performance micro-life must preserve character identity, expression intent, eye-line target, and continuity.

### Compact Runtime Profile

- The video prompt must compile internal analysis into a compact runtime prompt.
- Do not paste the full internal reasoning, validation checklist, or specification logic into `prompt_video.txt`.
- The specification may analyze richly, but the saved runtime prompt must be compact, executable, and focused on generation-critical instructions.
- The compact runtime prompt must preserve:

  1. Reference registry.
  2. Style firewall.
  3. Keyframe reference rules when keyframes are used.
  4. Surface fidelity lock.
  5. Scene grammar.
  6. Orientation, facing, and composition contract when relevant.
  7. Ambient life and performance micro-motion when relevant.
  8. Scene action.
  9. Scale lock when relevant.
  10. Shot plan.
  11. Continuity.
  12. Negative prompt.

- Do not expand every internal module into a long separate block unless the scene complexity requires it.
- Merge compatible modules when safe.
- Prefer compact blocks with direct executable language.
- Remove explanatory prose that does not affect generation.
- Avoid repeated negative phrasing across multiple sections.
- Avoid repeating raw image handles outside the reference registry.
- Avoid repeating the same continuity rule in multiple places unless repetition is required for critical preservation.

### Prompt Budget Profile

- Use a prompt budget profile for `prompt_video.txt`.
- Default compact video prompt target: 2500 to 4500 characters.
- Complex scene video prompt target: 4500 to 7000 characters.
- High-complexity or multi-reference prompt target: 7000 characters or more only when necessary.
- Absolute ceiling: stay below the current platform or model input limit when known.
- If a platform limit is supplied by the user, treat it as the hard ceiling.
- If the prompt risks exceeding the budget, preserve these elements first:

  1. Reference registry.
  2. Style firewall.
  3. Surface fidelity lock.
  4. Keyframe reference rules when keyframes are used.
  5. Orientation and facing contract when relevant.
  6. Scale lock when relevant.
  7. Shot plan.
  8. Continuity.
  9. Negative prompt.

- Compress or remove:

  1. Repeated prose.
  2. Explanatory rationale.
  3. Duplicate style adjectives.
  4. Redundant continuity statements.
  5. Optional audio notes.
  6. Optional atmosphere elaboration.
  7. Non-critical long descriptions.

### Optional Keyframe Anchor Workflow

- A keyframe is a final-style still image used as a visual anchor for video generation.
- A storyboard sheet is not a keyframe.
- The storyboard reference controls structure only.
- A keyframe reference controls final visual appearance within its assigned coverage.
- Keyframe references may control final image style, lighting, texture, surface fidelity, material finish, character or subject finish, scale, orientation, shot-specific composition, and environment finish.
- Use keyframes when visual fidelity, surface texture, scale, orientation, or shot-specific composition is unlikely to remain stable from text and storyboard alone.
- Do not require keyframes for every scene.
- Do not generate one keyframe per panel by default.
- Generate the minimum number of keyframe prompts required to lock final visual style and high-risk visual facts.
- If keyframes are used, create `prompt_keyframes.txt` as a conditional output.
- If keyframes are not needed, do not create `prompt_keyframes.txt`.

Use one of these strategy values:

```yaml
keyframe_strategy:
  - none
  - single_global
  - cluster_anchors
  - per_shot_or_panel
```

Strategy definitions:

```text
none:
Use when the scene is simple, visual fidelity risk is low, references are sufficient, and the user does not request keyframe anchors.

single_global:
Use one final-style keyframe to anchor the entire scene. Appropriate when location, lighting, subject state, style, and camera axis remain mostly consistent.

cluster_anchors:
Use multiple keyframes grouped by visual continuity clusters. Appropriate when different panel ranges share stable location, lighting, subject state, camera axis, or style needs.

per_shot_or_panel:
Use one keyframe per shot or panel only when explicitly requested, when final-pass quality is required, or when each shot has materially different location, lighting, subject state, camera axis, interaction, scale, or composition risk.
```

### Keyframe Cluster Planner

```yaml
keyframe_plan:
  keyframe_strategy:
  keyframe_count:
  keyframe_coverage:
    - keyframe_id:
      covers:
      purpose:
      authority:
        visual_style_authority:
        surface_fidelity_authority:
        scale_authority:
        orientation_authority:
        relationship_authority:
        composition_authority:
      composition_authority_level:
      canonical_composition_reference:
      structure_source:
      lock_sources:
      approval_check:
      notes:
```

Allowed authority values:

```yaml
authority_value:
  - none
  - loose
  - partial
  - strong
```

- Decide keyframe count by visual continuity risk, not by panel count.
- A scene with many panels may need only one or a few keyframes if location, lighting, style, subject state, camera axis, and composition remain stable.
- A short scene may need multiple keyframes if it contains a high-risk close-up, a critical orientation relationship, a delicate interaction, a scale-sensitive object, or a surface-fidelity risk.
- Group panels or shots into keyframe clusters when they share location, lighting, atmosphere, style, camera axis, subject state, scale relationship, orientation relationship, interaction type, and composition purpose.
- Create separate keyframes when location, lighting condition, time of day, weather or atmosphere, character or subject state, prop or object state, scale relationship, subject orientation, facing relationship, camera axis, shot scale, procedure or interaction detail, critical emotional composition, or visual style source changes materially.
- Each keyframe prompt must state which panels or shots it covers, what it locks, what references it may use, what it must not include, and whether it controls global style, a cluster, or a specific shot.

### Keyframe Authority by Mode Router

- Do not assume every keyframe is an exact composition reference. Declare every authority field explicitly.
- In SCREENWRITER MODE, keyframes default to strong or partial style, surface, scale, orientation, and relationship anchors with `loose` composition authority. Use `strong` composition only for an intentionally shot-specific keyframe, insert, ECU, or critical composition proof.
- In APPRENTICE MODE, use `partial` composition authority for user-specified shot size, framing, angle, blocking, or camera intent; compiler-inferred elements remain `loose`.
- In AUTEUR MODE, use `strong` composition authority only when the keyframe matches the user-specified shot size, camera angle, blocking, subject placement, and shot order.
- A keyframe that does not match authoritative shot structure may remain a style or surface reference but must not gain strong composition authority.
- Multi-shot keyframes default to `loose` composition authority unless covered shots share compatible framing.
- Composition authority must never silently override the Mode Router, explicit user locks, or `APPROVED_STORYBOARD_REF`.

### Composition Authority Levels

```yaml
composition_authority_level:
  none:
    meaning: keyframe does not guide framing, crop, camera angle, or layout.
  loose:
    meaning: keyframe provides general relationship, spatial feeling, or broad staging but not exact framing.
  partial:
    meaning: keyframe preserves specific user-specified or structurally critical composition elements while leaving other framing details flexible.
  strong:
    meaning: keyframe is an exact or near-exact shot-specific composition reference for the covered shot.
```

- Use `strong` only for shot-specific keyframes or compatible grouped framing.
- Use `partial` when only named composition elements are canonical.
- Use `loose` for global style, scale, relationship, or orientation anchors unless intentionally shot-specific.
- Use `none` for a purely style, texture, or material reference.
- A keyframe may have strong style authority but loose composition authority, or strong surface authority with no scale authority.
- Insert and ECU keyframes may have strong composition authority for crop, contact point, object state, tool use, and visual proof.
- Do not let a loose keyframe override approved storyboard structure or explicit user shot instructions.

### Keyframe Authority Propagation

- Authority fields declared in `prompt_keyframes.txt` must become explicit downstream reference-use language in `prompt_video.txt`.
- Every keyframe registry entry must state covered range, all authority fields, composition authority level, and whether it is a canonical composition reference.
- For `strong` composition authority, state that the keyframe is canonical for covered framing, shot size, camera angle, crop, blocking, and required visual proof.
- For `partial`, list canonical elements and flexible elements.
- For `loose`, state that the keyframe is not an exact framing reference and is limited to the declared broad authorities.
- For `none`, state that the keyframe must not control framing, crop, camera angle, or shot size.
- Every covered shot in the Shot Plan must include a short executable keyframe-use sentence.
- Labels alone are insufficient; authority must be expressed as executable downstream language.

### Downstream Propagation Audit

- Every major upstream decision must have a downstream execution surface.
- A decision is executed only when it appears in a relevant prompt file, final response, or approval and repair checklist.
- Metadata-only labels are insufficient for production-critical constraints.
- Audit these paths before saving files:

  - Mode Router -> storyboard structure, video shot execution, final response.
  - Scene Grammar Router -> panel density, pacing, motion language, feedback intensity, Shot Plan.
  - Asset Authority Map -> Reference Registry, Style Firewall, aesthetic stack, Surface Fidelity Lock, negative prompt.
  - Lock Source Hierarchy -> Structural Lock Ledger, approval gate, repair priority, downstream wording strength.
  - Scale Contract -> storyboard anchors, keyframe prompt, video scale lock, negative prompt, compliance checklist.
  - Orientation and Facing Contract -> storyboard plan, keyframe prompt, video orientation block, Shot Plan, negative prompt.
  - Face-Like Surface Orientation -> storyboard prompt, keyframe prompt, video Shot Plan, negative prompt.
  - Structural Lock Ledger -> approval checklist, repair workflow, approved-storyboard requirement.
  - Keyframe authority fields -> keyframe prompt, video registry, Shot Plan, validation.
  - Surface Fidelity Lock -> keyframe prompt, video block, negative prompt.
  - Ambient Life by Shot Scale -> shot-specific video instructions.
  - ECU and Insert Crop Fidelity -> storyboard plan, keyframe prompt, video Shot Plan.
  - Storyboard State-Color Exception -> storyboard purity and video Style Firewall.
  - Prompt Budget Profile -> the actual compact runtime prompt.
  - Human Approval Gate -> final response and approved-reference naming.

- Revise the prompt structure before saving when a production-critical decision lacks a downstream execution surface.
- Label advisory rules as advisory. Mandatory rules must appear in the relevant downstream prompt or approval checklist.

### Keyframe Prompt Purity

- Keyframe prompts must generate single final-style still images.
- Keyframe prompts must not generate storyboard sheets.
- Keyframe prompts must not generate multiple panels unless the user explicitly requests a keyframe sheet.
- Keyframe images must not include panel borders, panel headers, captions, labels, notes, arrows, UI, subtitles, production marks, shot numbers, camera diagrams, gutters, project cards, or storyboard-sheet design.
- Keyframes must look like final video frames, not production documents.
- Keyframes may use storyboard structure as composition guidance, but they must not copy storyboard rendering style.
- Keyframes may use non-storyboard visual references for final style, lighting, texture, character finish, subject finish, material finish, and environment finish.
- Keyframes must preserve the Style Firewall: storyboard reference controls structure only; non-storyboard assets and explicit director text control final style.
- If a keyframe is generated for a shot-specific detail, it must focus on that detail and avoid unnecessary unrelated composition expansion.

### Surface Fidelity Lock

- The video prompt must include a Surface Fidelity Lock when visual references contain distinctive texture, medium, line quality, material finish, wear, imperfection, or handmade surface behavior.
- Surface Fidelity Lock preserves the authorized surface properties of visual references.
- Surface Fidelity Lock may include uneven line weight, broken or imperfect edges, visible medium grain, paper grain, pigment bloom, non-uniform skin or surface wash, material wear, scratches, stains, fabric irregularity, hair or fur irregularity, surface aging, matte or glossy behavior, hand-painted instability, and material-specific texture.
- Do not clean up, polish, smooth, simplify, normalize, beautify, or genericize subjects beyond the authorized reference style.
- Do not erase stains, grain, wear, texture, material irregularity, handmade marks, or distinctive surface behavior when those details are part of the authorized references.
- Do not convert a rough, worn, handmade, analog, textured, or imperfect reference into a clean commercial default style unless the user explicitly requests that change.
- If the user explicitly requests a cleaner, more polished, more stylized, more realistic, more anime-like, more graphic, or more minimal result, follow the user instruction and state that the requested style overrides the default surface fidelity preservation.

### Composition Lock

- Define a Composition Lock when a shot depends on a specific visual proof, action result, reaction target, or subject-object relationship.
- Composition Lock may preserve reaction target in frame, object or subject position, tool contact, action result, removed or changed object state, indicator state, display surface, eye-line target, scale relationship, foreground-background relationship, shared frame relationship, or critical offscreen anchor.
- Do not let emotional framing replace required procedural proof, action result, or continuity evidence.
- If a reaction shot depends on another subject or object, keep the target visible when possible.
- If the target must remain offscreen, state the exact offscreen eye-line anchor.
- If a shot must prove that an action occurred, include the visual evidence in the frame.
- If a subject must face another subject, do not rotate it toward the camera only to improve viewer visibility.
- Propagate every relevant face-like surface direction into the video Orientation block, covered keyframe prompts, Shot Plan, and negative prompt.
- State face-like surface visibility as oblique, partial, foreshortened, side-angled, rim-visible, or frontal only when explicitly required.
- Classify face-like surface direction with the Lock Source Hierarchy.

### Readable Micro-Motion

- Micro-motion must be subtle but readable.
- Do not describe micro-motion only with vague phrases such as `barely moves`, `slightly shifts`, or `very subtle` when execution requires visible motion.
- For micro-motion that must be seen, specify count, direction, timing, subject, intensity, and whether it repeats or happens once.
- Ambient Life is independent environment motion.
- Performance Micro-Life is subject performance motion.
- For observational scenes, conversational scenes, and long-held soft kinetic scenes, include subtle but readable Ambient Life unless the user requests total stillness.
- For held human, creature, or character shots, include subtle but readable Performance Micro-Life when appropriate.
- Ambient Life may include fabric movement, plant movement, dust movement, steam movement, water movement, reflection movement, light variation, shadow movement, air movement, distant exterior movement, or small background object motion.
- Performance Micro-Life may include blink, breath, swallow, eye-line adjustment, hand tension change, posture settling, shoulder release, facial stillness change, grip release, or small weight shift.
- Do not over-animate quiet scenes.
- Do not add new story events.
- Do not distract from the main action.
- Do not force blinking into every shot.
- Do not place a blink, breath, or micro-motion during a critical fixed stare, exact contact moment, impact, or precision action unless it supports the performance.
- Prefer direct executable phrasing that states a single motion, count, timing, and result rather than vague subtlety.
- Use generic wording only. Do not include scene-specific examples.

### Ambient Life by Shot Scale

- Assign ambient life according to shot scale and visible environment area.
- For wide and medium shots, prefer one visible low-intensity environmental motion when appropriate.
- For medium close-up and close-up shots, use edge-of-frame environmental motion only when visible and useful; prioritize performance micro-life, eye-line, breath, hand tension, posture, object response, or nearby motion.
- For ECU and insert shots, do not force environmental motion. Prioritize contact, resistance, texture, tool motion, object-state change, surface behavior, and micro-action arc; use `ambient: none needed` when environment is not visible.
- For observational scenes and soft kinetic scenes, distribute ambient life where it can actually be seen.
- Do not place the only environmental ambient motion in a close-up when a wider shot is more suitable.
- Do not over-animate the environment or create new story events.

## 13. Validation Rules

Use this canonical modular checklist before completing a future prompt-generation run. Each mandatory production control must appear in a relevant downstream prompt, approval check, repair note, or final response; metadata-only labels do not satisfy the checklist.

### Canonical v2.3.1 Modular Checklist

Version and structure:

- The specification version is `2.3.1` and all 13 top-level numbered sections remain.
- Required outputs remain `prompt_storyboard.txt` and `prompt_video.txt`; `prompt_keyframes.txt` remains conditional.

No media execution:

- Prompt compilation creates prompt files only and does not execute prompt text or call media-generation tools.

Routing and output contract:

- Director maturity mode and scene grammar are resolved once, preserve explicit shot instructions, and appear in storyboard, video, and final-response surfaces.
- The two required prompt files are always created; keyframe prompts are created only for a non-`none` strategy or explicit request.
- The final response lists only created files and includes routing, keyframe strategy, and approval gates.

Storyboard production rules:

- Panel order, count, shot scale, frozen-instant staging, camera-side translation, and continuity follow the selected mode and director locks.
- Board presentation, headers, margins, and gutters remain outside structural panel interiors.
- Inserts and ECUs preserve tight crop and required visual proof.
- State-color markers remain sparse, schematic, structural, and excluded from final-video style authority.
- Storyboard purity blocks finished illustration, duplicate bodies, extra subjects or props, panel-interior text, UI, arrows, and temporal ghost poses.

Asset, style, and surface authority:

- Every asset has a generic role and explicit authority; raw runtime handles remain in the Reference Registry.
- The storyboard remains structural only; assigned non-storyboard assets govern final appearance within their authority.
- Style Firewall and Surface Fidelity Lock prevent storyboard-style leakage, generic cleanup, unauthorized polish, and material drift.
- Scale contracts are stated in text and accidental resizing is blocked downstream.

Lock Source Hierarchy:

- Relevant scale, orientation, facing, composition, object-state, shot, and action-proof locks are classified by source.
- Explicit user locks are preserved; inferred locks are labeled; compiler preferences are not presented as director instructions.

Structural Lock Ledger and compliance:

- Storyboard prompts include a concise source-classified ledger when structural locks matter.
- Storyboards are checked before downstream use; hard-lock failures require repair or regeneration.
- Inferred-lock failures are surfaced for review; unapproved storyboards do not become strong downstream references.
- Repair notes are short, structural, preserve passing locks, and treat manual repair as normal production work.

Keyframe planning and purity:

- Strategy and count follow visual continuity risk rather than panel count alone.
- Every keyframe states coverage, purpose, structure source, lock sources, authority, and approval check.
- Keyframe prompts produce final-style single frames without storyboard layout, headers, labels, notes, UI, arrows, or text.
- Keyframes require approved storyboard structure before execution.

Keyframe authority by mode:

- Keyframe authority respects AUTEUR, APPRENTICE, and SCREENWRITER mode.
- SCREENWRITER keyframes default to loose composition unless shot-specific; APPRENTICE uses partial authority for user-specified elements; AUTEUR uses strong authority only for matching specified shots.
- Every keyframe declares visual style, surface fidelity, scale, orientation, relationship, and composition authority using `none`, `loose`, `partial`, or `strong`.
- Multi-shot keyframes do not imply strong composition authority by default.

Keyframe Authority Propagation:

- Keyframe authority fields appear in `prompt_keyframes.txt` and propagate into `prompt_video.txt`.
- Every keyframe registry entry states coverage, all authority fields, composition level, and canonical-composition status.
- Strong composition authority becomes canonical framing language in the Reference Registry and Shot Plan.
- Partial composition authority lists canonical and flexible elements.
- Loose composition authority is explicitly prevented from becoming exact framing authority.
- No keyframe silently overrides the Mode Router, explicit user locks, or `APPROVED_STORYBOARD_REF`.

Orientation and composition:

- Face-like surfaces do not rotate toward the viewer unless explicitly required; visibility does not override relationship orientation.
- Face-like surface direction has a lock source.
- Composition Lock preserves reaction targets, action proof, object state, and critical relationships.

Ambient life by shot scale:

- Wide and medium shots receive visible ambient life when appropriate.
- MCU and CU shots use ambient life only when visible and useful.
- ECU and insert shots prioritize contact, texture, state, and micro-action; ambient life is not forced into invisible areas.

Compact runtime and execution:

- `prompt_video.txt` is compact, executable, within the applicable prompt budget, and retains all generation-critical controls.
- Shot Plan preserves pacing, performance pressure, action, reaction target, micro-action arc, keyframe use, feedback, readable micro-motion, and shot-scale-appropriate ambient life.
- Hard cuts are the default between separate shots unless the director specifies another transition; continuous takes remain uncut unless directed otherwise.
- Negative rules block identity, scale, orientation, state, spatial, style, anatomy, extra-subject, text-artifact, and camera drift.

Organization and generic wording:
