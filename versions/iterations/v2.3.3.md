## 2. Compiler Boundary

This specification is a prompt compiler for director scene text, optional shot instructions, and optional visual assets. It routes mode and scene grammar, maps asset authority, preserves continuity and shot intent, and creates directly executable prompts for ChatGPT Image 2 and Seedance. It supports both reference-based video generation and standalone text-to-video generation.

- The current agent generates and saves `.txt` prompt files only; it does not execute downstream prompts.
- The current agent does not generate images or videos unless the user separately requests media generation outside this compiler workflow.
- `prompt_storyboard.txt` contains only an executable ChatGPT Image 2 storyboard prompt.
- Conditional `prompt_keyframes.txt` contains only executable ChatGPT Image 2 keyframe prompts.
- `prompt_video.txt` contains only an executable Seedance video prompt.
- Generated prompt files contain no workflow explanations, approval gates, repair instructions, validation text, diagnostics, checklists, missing-asset reports, or internal compiler reasoning.
- Internal routing, authority, priority, compression, and propagation audits remain compiler logic and become concise executable downstream instructions only where relevant.
- The final response returns created file paths and a compact routing summary only.
- A generated storyboard is a candidate structural board; inspection, selection, repair, cropping, or regeneration happens outside generated prompt files.
## 3. Input Package

Before routing or prompt generation, inspect the complete input package:

```yaml
input_package:

  explicit_shot_instructions:
  uploaded_visual_assets:
    - asset_handle:
      filename:
      user_caption:
      visible_content_summary:
      inferred_asset_roles:
      confidence:
      notes:
  requested_output_slug:
```

Apply these rules:

- The director scene description is always the primary intent source.
- Explicit shot instructions override compiler-inferred shot structure.
- Uploaded visual assets must be inspected and assigned roles before prompt generation.
- Asset order must never define asset meaning.
- Do not assume `@image1`, `@image2`, or any other image handle has a fixed role before asset mapping.
- Image handles such as `@image1`, `@image2`, and `@image3` are runtime references assigned by the environment where the future workflow is executed.
- A single asset may hold multiple roles.
- If image content can be inspected, use visible content, filename, user caption, and scene context to assign asset roles.
- If image content cannot be inspected, rely on filename, user caption, and scene context only.
- If asset role assignment is ambiguous, assign the safest role and record the uncertainty in `notes`.
- If an asset cannot be safely assigned, mark it as `unused_or_ambiguous_reference`.
- Use generic asset roles and subject IDs according to actual input.
- Do not assume that every input contains a character, mechanical subject, vehicle, prop, object, or environment reference.
- Use `CHARACTER_1`, `CHARACTER_2`, `SUBJECT_1`, `SUBJECT_2`, `PROP_1`, `OBJECT_1`, `MECH_1`, `VEHICLE_1`, and `ENVIRONMENT_1` only when the corresponding role is relevant.
- A generated prompt may use shorter IDs only after the asset map assigns them clearly.

## 4. Mode Router

Route the input to exactly one director maturity mode.

```text
AUTEUR MODE:
Use when the user provides a complete shot list, explicit ordered shot structure, explicit panel structure, or complete camera/framing instructions. Execute the supplied structure exactly. Do not re-segment, reorder, add, delete, or reinterpret shots.

APPRENTICE MODE:
Use when the user provides partial shot intent, required shot types, partial camera direction, incomplete panel logic, or selected framing constraints. Preserve every explicit user constraint. Complete only the missing structure.

SCREENWRITER MODE:
Use when the user provides only a scene idea, script fragment, action flow, emotional situation, or visual description without explicit shot structure. Infer shot structure from narrative, visible behavior, geography, action, and continuity needs.
```

Routing rules:

- Route once before normalization or prompt generation.
- Do not re-route downstream.
- Treat numbered shot entries, `Shot 1`, `Shot 01`, `CU`, `MS`, `WS`, close-up, medium shot, wide shot, tracking, pan, tilt, dolly, crane, static camera, handheld, locked-off, insert, reaction shot, POV, master shot, or explicit camera movement as structural evidence only when they function as shot instructions.
- Do not classify input as AUTEUR MODE only because it uses the word `scene` in ordinary prose.
- If the input includes both scene prose and explicit shot instructions, choose AUTEUR MODE or APPRENTICE MODE according to shot completeness.
- Print the selected mode as the first line of every generated prompt file using exactly one of:

  - `[MODE: AUTEUR]`
  - `[MODE: APPRENTICE]`
  - `[MODE: SCREENWRITER]`

Keyframe composition authority must respect the selected mode:

- In AUTEUR MODE, user-specified shot structure remains authoritative. Strong keyframe composition authority is allowed only when the keyframe matches the specified shot.
- In APPRENTICE MODE, keyframes may have partial composition authority for user-specified elements; compiler-inferred elements remain flexible.
- In SCREENWRITER MODE, keyframes default to loose composition authority unless intentionally generated for one specific shot, insert, ECU, or critical composition proof.
- Composition authority must never silently override the Mode Router.

## 5. Scene Grammar Router

Select the scene grammar after selecting the director maturity mode. The director maturity mode determines how much shot structure the user controls. Scene grammar determines pacing language, panel density, feedback intensity, camera execution style, and video execution language.

Use this analysis schema:

```yaml
scene_grammar_analysis:
  scene_grammar_type:
  continuous_take:
  camera_execution:
  pacing_profile:
  feedback_intensity:
  motion_intensity:
  notes:
```

Allowed values:

```yaml
scene_grammar_type:
  - kinetic_scene
  - observational_scene
  - conversational_scene

continuous_take:
  - true
  - false

camera_execution:
  - locked_off
  - handheld_follow
  - slow_track
  - dolly_push
  - lateral_track
  - orbit
  - static_coverage
  - mixed_coverage
  - director_specified

feedback_intensity:
  - low
  - medium
  - high

motion_intensity:
  - minimal
  - soft
  - moderate
  - aggressive
```

Grammar definitions:

```text
kinetic_scene:
Use for scenes driven by physical motion, combat, chase, escape, panic movement, slapstick, mechanical struggle, physical procedure with visible resistance, or fast cause-and-effect action. A kinetic scene can be soft, moderate, or aggressive. It is not always violent or high-impact.

observational_scene:
Use for scenes driven by stillness, duration, atmosphere, solitary behavior, careful procedure, object handling, quiet emotional observation, negative space, micro-movement, or slow spatial attention.

conversational_scene:
Use for scenes driven by dialogue, silence between characters, eye-line exchange, reaction timing, blocking distance, social pressure, refusal to answer, emotional negotiation, or relationship tension.
```

Classification rules:

- Select the scene grammar after selecting AUTEUR MODE, APPRENTICE MODE, or SCREENWRITER MODE.
- Scene grammar must not change the selected director maturity mode.
- Scene grammar must not change explicit shot count, shot order, framing, camera movement, or shot scale supplied by the director.
- If multiple grammar types are present, choose the dominant grammar that controls the main scene experience.
- If a scene contains physical motion but the emotional focus is quiet observation, choose `observational_scene` and set `motion_intensity` to `soft` or `minimal`.
- If a scene contains dialogue while characters are walking or moving, choose `conversational_scene` when the dialogue and reactions are the main event.
- If a scene contains a following one-take camera move, do not automatically classify it as `observational_scene`. Set `continuous_take` to `true` and classify the grammar by the scene's main dramatic engine.
- A following one-take chase or fight is `kinetic_scene` with `continuous_take` set to `true`.
- A following one-take walk-and-talk is `conversational_scene` with `continuous_take` set to `true`.
- A following one-take silent walk through a room, hallway, or landscape is `observational_scene` with `continuous_take` set to `true`.
- Classify scene grammar primarily from director text, explicit shot structure, action logic, dramatic engine, and the central readable event.
- Visual asset style, color, medium, lighting, atmosphere, or emotional finish must not change the scene grammar unless the user explicitly states that the asset mood should determine pacing or scene behavior.
- Visual assets may influence final video appearance through the Asset Authority Map, but they must not replace director action logic when selecting scene grammar.
- If the scene's central readable event is a physical obstacle, mechanical struggle, stuck/free state, chase, fall, impact, object movement, or visible physical resistance, prefer `kinetic_scene` with `motion_intensity` set to `soft`, `moderate`, or `aggressive` according to tone.
- If a physical event is secondary and the main experience is stillness, care, waiting, emotional observation, or careful attention, choose `observational_scene`.
- A gentle domestic mechanical problem may be `kinetic_scene` with `motion_intensity: soft` and `feedback_intensity: low`.
- Do not convert a soft kinetic scene into `observational_scene` only because the visual assets have a warm, painterly, quiet, or gentle style.

Control rules:

- Scene grammar controls pacing language, panel density, feedback intensity, rhythm marker choice, physical verb choice, audio design language, and the level of environmental or mechanical response.
- Scene grammar does not control final video style.
- Scene grammar does not override the Asset Authority Map.
- Scene grammar does not override the Final Style Protection Stack or Style Control.
- Scene grammar does not authorize storyboard rendering style to leak into final video style.

## 6. Asset Authority Map

Create an internal asset authority map before writing either prompt file. Assign every uploaded asset one or more of these roles:

```yaml
asset_roles:
  - storyboard_structural_reference
  - keyframe_visual_reference
  - character_reference
  - creature_reference
  - subject_reference
  - prop_or_object_reference
  - mechanical_subject_reference
  - vehicle_reference
  - environment_layout_reference
  - style_reference
  - lighting_reference
  - texture_reference
  - atmosphere_reference
  - scale_reference
  - unused_or_ambiguous_reference
```

Role definitions:

| role | controls | notes / limits |
| --- | --- | --- |
| `storyboard_structural_reference` | Shot order, framing, staging, camera placement, action beats, screen direction, spatial continuity | Structure only; never final video style. |
| `keyframe_visual_reference` | Visual style, lighting, texture, surface fidelity, subject finish, scale, orientation, shot-specific composition, material treatment | Limited to declared coverage and authority. |
| `character_reference` | Identity, face, proportions, silhouette, wardrobe, hair, posture, expression range, movement quality, character finish | May contribute character-specific rendering style unless explicitly limited. |
| `creature_reference` | Identity, anatomy, silhouette, surface, motion and expression limits, scale, finish | Subject-specific authority only. |
| `subject_reference` | Primary non-character subject properties | Use when no more specific role fits. |
| `prop_or_object_reference` | Shape, size, state, material, surface, functional limits, texture, interaction behavior | May contribute visible material, finish, and texture. |
| `mechanical_subject_reference` | Mechanical design, moving parts, facing surfaces, indicators, material boundaries, behavior limits | Use for robots, machines, devices, and mechanical tools. |
| `vehicle_reference` | Design, scale, orientation, functional surfaces, material treatment, motion constraints | May contribute visible material, finish, and texture. |
| `environment_layout_reference` | Layout, architecture, entrances, exits, surfaces, furniture, set anchors, proportions, screen direction | May contribute environment materials, finish, texture, lighting, and atmosphere within authority. |
| `style_reference` | Final medium, finish, texture, color, line or edge behavior, lighting, aesthetic treatment | Highest non-user authority for overall final style. |
| `lighting_reference` | Source direction, softness, contrast, color temperature, exposure mood | Lighting authority only. |
| `texture_reference` | Material grain, surface behavior, brush, fabric, organic, mechanical, environmental, or atmospheric texture | Texture and surface authority only. |
| `atmosphere_reference` | Weather, haze, mist, dust, steam, air density, reflections, environmental mood | Atmosphere authority only. |
| `scale_reference` | Relative size among subjects, objects, architecture, and environment anchors | Scale authority only. |
| `unused_or_ambiguous_reference` | None | Must not influence generation. |

Asset authority rules:

- Do not hardcode `@image1` as storyboard, `@image2` as character, or any fixed asset order.
- The future workflow has two phases:

  1. Generate `prompt_storyboard.txt`.
  2. Use the resulting storyboard image as a possible structural reference when generating or using `prompt_video.txt`.

- If a storyboard image has already been generated from `prompt_storyboard.txt`, assign that storyboard image the role `storyboard_structural_reference`.
- In `prompt_video.txt`, include a prominent `REFERENCE REGISTRY` near the top.
- The `REFERENCE REGISTRY` must include the storyboard reference slot and must state each available asset handle, its assigned role, and its authority.
- If no image references are available, the video prompt must remain usable as a standalone text-to-video prompt.
- Do not rely exclusively on image references for subject, action, environment, camera, or continuity.
- Restate essential subject, action, environment, camera, continuity, and style information in text.
- All non-storyboard visual assets contribute to final video aesthetic continuity unless the user explicitly excludes them.
- Dedicated style reference assets have highest authority for overall final video style.
- Character reference assets contribute character identity and character-specific rendering style, including line quality, stylization boundary, facial finish, fabric finish, hair treatment, color behavior, texture behavior, and visible material treatment for that character.
- Creature, vehicle, robot, prop, tool, device, object, or product reference assets contribute design, scale, material boundaries, mechanical or functional design when relevant, object-specific color behavior, surface treatment, texture behavior, and rendering finish for those subjects.
- Environment reference assets contribute layout, lighting, atmosphere, spatial materials, color behavior, environmental texture, and overall location finish.
- Lighting, texture, and atmosphere references contribute their assigned visual properties only.
- The generated storyboard image never contributes final video style.
- If multiple non-storyboard assets have compatible visual styles, harmonize them into one coherent final video aesthetic stack.
- If non-storyboard assets conflict in style, prioritize:

  1. Explicit user instruction.
  2. Dedicated style reference.
  3. Environment reference for lighting and atmosphere.
  4. Character reference for character rendering.
  5. Object, prop, tool, device, vehicle, creature, or robot reference for that subject's rendering.

- Do not treat `character_reference` as identity-only by default. A character reference also contributes character-specific final rendering style unless the user explicitly limits it to identity only.
- Do not infer that an asset contributes only identity, layout, or geometry if it also visibly defines rendering finish, line treatment, color behavior, material texture, or stylization boundary.
- Assign generated final-style keyframe images the role `keyframe_visual_reference` and record their panel or shot coverage and visual authority.
- Keyframe references contribute final-style appearance only within their assigned coverage and never replace storyboard structural authority.
- When visual references contain distinctive surface behavior, record the authorized line quality, medium grain, wear, imperfection, texture, material finish, and stylization boundary in the asset notes.
- Do not use `robot_or_prop_reference` as a default role name.
- Do not use `R1` as a default placeholder in templates.
- Do not use mechanical-subject wording in templates unless the current input contains a mechanical subject.
- Use `MECH_1` only for mechanical subjects.
- Use `PROP_1` or `OBJECT_1` for non-mechanical props or objects.
- Use `SUBJECT_1` for a primary non-character subject when no more specific role is appropriate.
- Do not force every scene into character-plus-object language.

### Lock Source Hierarchy

```yaml
lock_source_hierarchy:
  explicit_user_lock:
    priority: highest
    meaning: directly stated by the user, explicit shot instruction, explicit scene constraint, or explicit asset instruction.
  asset_inferred_lock:
    priority: high
    meaning: inferred from clear visual asset evidence, filename, asset sheet notes, visible scale, visible orientation, visible design, or visible material state.
  action_inferred_lock:
    priority: medium
    meaning: inferred from action logic, interaction logic, eye-line logic, tool access, relationship blocking, or cause-effect readability.
  compiler_preference:
    priority: lowest
    meaning: chosen by the compiler for clarity, aesthetics, readability, or conventional staging when no stronger lock exists.
```

- Classify every relevant scale, orientation, facing, composition, object-state, shot-order, shot-size, and action-proof constraint by source.
- Explicit user locks must be preserved unless they directly conflict with a later explicit user instruction.
- Asset-inferred locks are strong but must not override explicit user locks.
- Action-inferred locks are recommended structural logic and must be labeled as inferred.
- Compiler preferences must never be presented as explicit director instructions.
- If an inferred lock may affect interpretation, record it internally and translate it into appropriate executable wording strength. Do not expose source labels, review notes, or internal audit language in generated prompt files.
- Do not overstate inferred relationships as hard user commands or invent locks that conflict with user text or asset evidence.
- Use this wording pattern: `Source: explicit_user_lock | asset_inferred_lock | action_inferred_lock | compiler_preference`.
- Keep lock-source labels inside compiler analysis only. Do not output `Source:` labels in `prompt_storyboard.txt`, `prompt_keyframes.txt`, or `prompt_video.txt`.
- Translate source priority into direct executable wording strength rather than visible metadata.

## 7. Continuity Firewall

The Continuity Firewall governs identity, space, props, mechanics, and style across the storyboard and video prompts.

### 7.1 Identity and Subject Continuity

- Use stable role-based IDs such as `CHARACTER_1`, `CHARACTER_2`, `SUBJECT_1`, `PROP_1`, `OBJECT_1`, `MECH_1`, `VEHICLE_1`, or `ENVIRONMENT_1` only when relevant to the input.
- Preserve character identity across all storyboard panels and video beats.
- Preserve creature identity, primary subject design, prop or object identity, mechanical subject design, and vehicle identity across storyboard panels, keyframes, and video shots when those roles are present.
- Preserve face, silhouette, wardrobe, body proportions, hair, key props, and movement quality when supported by director text or assets.
- Do not redesign, age-shift, beautify, caricature, merge, or replace characters unless explicitly requested.
- Use asset references only within their assigned authority roles.

### 7.2 Spatial and Prop Continuity

- Preserve room layout, thresholds, entrances, exits, furniture placement, screen direction, camera axis, and set anchors.
- Preserve prop state and mechanical state across panels and video beats.
- For mechanical subjects, preserve design, moving parts, functional surfaces, indicator behavior when present, material boundaries, state, resistance, and movement limitations.
- If multiple panels occur in the same location, describe them as the same layout rather than a redesigned space.
- Allowed changes must come from the director description or the shot logic.

### 7.3 Scale Continuity

- Define a Scale Contract whenever characters, creatures, vehicles, robots, props, tools, devices, objects, furniture, architecture, or environment anchors appear together.
- The Scale Contract must describe relative size relationships in text.
- Use stable comparative anchors such as head size, shoulder height, waist height, knee height, hand size, doorway height, bed height, table height, chair height, floor tile scale, object-to-body proportion, or object-to-environment proportion.
- If a subject, prop, object, or environment element has a director-specified scale, preserve it across storyboard panels and video shots.
- If a scale reference asset is provided, assign it the role `scale_reference` and record its authority inside the asset notes.
- If no scale reference asset is provided, infer a text-based Scale Contract from director text, visual assets, and spatial context.
- Do not let foreground placement, wide-angle distortion, furniture scale, environment perspective, or shot framing accidentally resize a character, creature, vehicle, robot, prop, tool, device, object, or environment anchor.
- Do not rely only on image references for scale continuity. State the key scale relationships in text.

### Orientation / Facing / Face-Like Surface Contract

- Preserve meaningful fronts, backs, sides, screens, labels, sensors, display surfaces, doors, handles, windows, tools, direction of travel, screen direction, and facing relationships when relevant.
- State which side faces the camera, another subject, and the action; which side remains visible; and which side must not flip.
- Use the principle: visible enough for the viewer, but oriented according to the scene relationship.
- Face-like surfaces, including faces, eyes, lenses, sensors, windows, screens, dashboards, muzzles, cameras, and indicators, are high-risk orientation surfaces.
- A face-like surface must not rotate toward the camera only for visual clarity when it should face another subject, action target, or offscreen source.
- Use oblique, partial, foreshortened, side-angled, rim-visible, or three-quarter non-frontal wording when needed.
- Preserve explicit relationships. Infer only the safest relationship required by action or eye-line logic, without conflicting with user intent.
- Apply the Lock Source Hierarchy internally and convert it to executable wording strength. Do not expose `Source:` labels in generated prompt files.

### Final Style Protection Stack

#### Style Firewall

- The storyboard image controls structure only and never final video style.
- Do not transfer storyboard sheet layout, borders, headers, labels, UI, graphite marks, paper texture, monochrome palette, state-color markers, construction marks, or storyboard rendering style into final video.
- Final video style may come only from explicit director text, assigned non-storyboard visual assets within their authority, and final-style keyframes within declared authority.
- Harmonize authorized non-storyboard sources without cleaning, beautifying, polishing, redesigning, normalizing, or genericizing subjects beyond their authority.

#### Style Survival

Style Survival carries the most important final visual finish from assigned non-storyboard references into `prompt_video.txt`: medium or rendering stack, line or edge behavior, surface texture, color behavior, lighting behavior, subject-specific finish, and environment finish. It must be compact and must never use storyboard rendering style as a source.

#### Surface Fidelity Lock

- Surface Fidelity Lock conditionally preserves authorized texture, medium, material finish, wear, imperfection, line quality, handmade surface behavior, and stylization boundaries across keyframes and video shots.
- It prevents smoothing, cleaning, polishing, beautifying, or genericizing distinctive authorized surfaces unless explicit user direction overrides them.

## 8. Storyboard Prompt Rules for ChatGPT Image 2

`prompt_storyboard.txt` must instruct ChatGPT Image 2 to generate a storyboard sheet image, not a final video.

- Use the selected mode as the first line.
- Generate a compact storyboard sheet prompt.
- Optimize the storyboard sheet for readable production planning.
- Use the minimum panel count required for clear cause and effect.
- In AUTEUR MODE, preserve exact shot count, shot order, framing, camera movement, and shot scale.
- In APPRENTICE MODE, preserve all explicit shot instructions and complete only missing structure.
- In SCREENWRITER MODE, infer panel count and camera structure from action, geography, visible behavior, and continuity needs.
- Each panel must represent one frozen instant.
- Each panel must contain one dominant visual beat.
- Do not describe temporal sequences inside a single panel.
- Do not use sequential wording inside panel descriptions, including temporal use of `then`, `after`, `before`, `first`, `next`, `later`, `gradually`, `continues`, or `remains ... then`.
- If a listed word is used spatially rather than temporally, rewrite it to avoid ambiguity.
- Use visible behavior instead of abstract emotion.
- Convert psychology into posture, spacing, eye-line, hand tension, blocking, object state, or camera distance.
- Do not render detailed facial anatomy, finished facial illustration, beauty rendering, or character-design detail inside storyboard panels.
- However, when an emotional reaction is the main visual beat, allow minimal expression marks required for readability, such as eye-line direction, brow angle, head tilt, shoulder release, mouth curve, or a small smile.
- Minimal expression marks must remain schematic and production-board level. They must not become finished facial rendering.
- Translate director phrases such as `behind camera`, `offscreen behind camera`, `from behind the camera`, or `toward the camera-side source` into visible composition and blocking language.
- Do not rely on abstract camera-position wording when writing panel descriptions.
- Use visible terms such as `near-camera foreground edge`, `camera-side doorway`, `camera-side threshold`, `foreground entrance`, `walking away into depth`, `looking back toward the camera-side source`, or `eye-line aimed toward the near-camera offscreen area`.
- Preserve the director's intended geography, but express it as a visible frame relationship.
- Panel interiors must contain only visual staging: characters, environment, props, poses, effects, framing, and composition.
- Panel interiors must not contain text, arrows, captions, speech bubbles, subtitles, labels, diagrams, UI, timing marks, camera rigs, technical overlays, duplicate bodies, or ghost poses.
- Panel numbers, camera notes, shot names, and other metadata must stay outside panel image areas.
- Default storyboard panel rendering is production-board line art: open-outline silhouettes, thin graphite linework, simplified forms, broad negative space, paper-white field, sparse construction marks, no filled regions, no rendered lighting, no gradients, no material finish, no painterly texture, no photorealistic detail.
- Do not let the storyboard become finished manga line art, final illustration, concept art, or video-style artwork. Preserve structural readability over beauty inside panels.
- Visual assets may control storyboard identity, geometry, proportions, prop shape, and environment layout.
- Visual assets must not transfer color, lighting, texture, painterly finish, material finish, or final-video style into storyboard panel interiors unless explicitly requested.
- The storyboard prompt must not include a Director Strip.
- The storyboard prompt must include the selected scene grammar in a compact text field outside the panel image areas.
- Scene grammar may influence panel density and shot sampling, but it must not override explicit director shot instructions.
- For `kinetic_scene`, use enough panels to make physical cause-and-effect readable. Prioritize contact state, directional force, body position, object state, impact timing, mechanical resistance, and visible result.
- For `observational_scene`, use fewer panels unless the director requests more. Prioritize negative space, stillness, slow body movement, spatial duration, object state, environmental texture, light behavior, and small visible changes.
- For `conversational_scene`, prioritize eye-line, blocking distance, body orientation, pauses, reaction timing, hand behavior, seated or standing position, and spatial relationship between speakers.
- For `continuous_take: true`, treat panels as sampled phases of one uninterrupted camera path, not separate cuts, unless the director explicitly requests otherwise.
- For `continuous_take: true`, state the continuous camera path in `CAMERA CONTINUITY`.

### Storyboard Sheet Shell

- Storyboard panel interiors remain structural and de-stylized; sheet polish comes from layout, spacing, hierarchy, headers, margins, gutters, and restrained exterior design.
- Keep all presentation design outside panel interiors and do not increase facial, clothing, background, shading, color, texture, or rendering detail to create polish.
- Place a short, consistent header outside every panel unless the user explicitly requests no headers: `P## / shot size / beat name`.
- Enforce panel order through grid order, `P##` order, and prompt text, not headers alone.
- No storytelling text, captions, arrows, labels, UI, subtitles, diagrams, decorative illustrations, false props, logos, or production paperwork may appear inside panels.

### Insert and ECU Crop Fidelity

- If a storyboard panel is labeled `insert`, `detail`, `CU`, `ECU`, `extreme close-up`, `macro`, or equivalent, the panel must crop tightly around the required visual information.
- Do not automatically widen an insert or ECU panel into a character bust shot, medium shot, room view, or general emotional close-up.
- For procedure, contact, object state, tool use, display state, texture detail, or physical resistance, the crop must prioritize the relevant hands, tools, surfaces, contact points, object state, or visual evidence.
- Only include face, torso, room background, or wider context in an insert or ECU if the director explicitly requests it or if the detail cannot read without that context.
- If the shot label and the description conflict, preserve the director's explicit intent and clarify the crop in prompt text.
- For storyboard sheets, insert and ECU panels must remain single frozen instants, not miniature temporal sequences.

### Storyboard State-Color Exception

- Storyboard panel interiors are monochrome or de-stylized by default.
- A sparse schematic state-color marker is allowed only when color is essential to understanding a state, signal, status, warning, screen, light, material change, injury, magical effect, or other critical visual condition.
- State-color markers must be minimal.
- State-color markers must not create final illustration style.
- State-color markers must not become lighting, palette, atmosphere, texture, or final video style authority.
- State-color markers must not override Style Control or the Style Firewall layer.
- If color is not essential to state readability, express the state through shape, position, contrast, line marks, or composition instead.
- If a state-color marker is used in the storyboard prompt, explicitly state that it is schematic and structural only.

### Internal Structural Reasoning

- The compiler may internally apply the Lock Source Hierarchy and Downstream Propagation Audit to choose and prioritize scale, orientation, facing, composition, state, shot, and action-proof constraints.
- Convert production-critical constraints into short direct visual commands under `Critical visual locks`, panel descriptions, or negative constraints.
- Omit internal compiler reasoning from the generated storyboard prompt.
- Face-like surface orientation, insert or ECU crop, state-color exceptions, scale, and action proof remain executable visual constraints when relevant.
## 9. Storyboard TXT Template

The saved `prompt_storyboard.txt` must be a compact executable ChatGPT Image 2 prompt using this shape:

```text
[MODE: AUTEUR | APPRENTICE | SCREENWRITER]

Create a 16:9 clean production storyboard sheet.

Title: [short title]

Layout:
- [panel count and arrangement]
- Use compact headers outside each panel: P## / shot size / beat name
- Clean even gutters and margins
- Keep all panel headers and sheet metadata outside panel interiors

Reference use:
```

## 10. Video Prompt Rules for Seedance

Apply these rules:

- Performance pressure must match the selected scene grammar, feedback intensity, and motion intensity.

- For `motion_intensity: soft`, use low or medium performance pressure by default.

- For `motion_intensity: aggressive`, high performance pressure is allowed when supported by the director's action logic.

#### Surface Fidelity Escalation Rule

Surface Fidelity is not a free creative judgment. Decide it from evidence after the Asset Authority Map and before writing `prompt_video.txt`.

Use a separate `[SURFACE FIDELITY LOCK]` only when at least one primary trigger is present.

Primary triggers:

1. `explicit_user_lock`: the user explicitly asks to preserve texture, material finish, roughness, handmade quality, imperfection, wear, stains, grain, line quality, analog medium, or non-polished finish.
2. `asset_inferred_lock`: a non-storyboard visual reference visibly contains distinctive surface behavior, and smoothing, cleaning, polishing, beautifying, or genericizing it would change the subject, style, or material identity.
3. `role_authority_lock`: an assigned non-storyboard reference role has authority over texture, material, finish, surface behavior, medium, line quality, or visible imperfection.
4. `shot_readability_lock`: an explicit or generated shot depends on surface readability, such as an insert, ECU, macro, close-up, object handling, procedural contact, tool contact, mechanical contact, skin, fabric, hair, fur, material detail, or texture proof.

Secondary trigger:

5. `model_default_risk`: the model is likely to clean, smooth, gloss, normalize, commercialize, anime-clean, photoreal-clean, or genericize the result.

`model_default_risk` cannot trigger a separate block by itself; it can only upgrade a lock when a primary trigger exists. With weak evidence, keep surface fidelity as one compact line inside `[STYLE CONTROL]`. With no primary trigger, omit the separate block. When uncertain, compress it into Style Control or omit it. Storyboard references never trigger Surface Fidelity.

### Micro-Motion Layer

- `ambient life` is independent, low-intensity environmental motion.
- `performance micro-life` is subtle subject performance motion.
- `environmental feedback` is an environment response caused by subject action.
- `mechanical feedback` is a mechanical response caused by subject action or device behavior.
- Wide and medium shots may include one visible low-intensity ambient motion when appropriate.
- Close-ups prioritize performance micro-life, eye-line, breath, hand tension, object response, or nearby edge motion.
- ECU and insert shots do not force ambient motion; prioritize contact, resistance, texture, tool motion, object-state change, surface behavior, or a micro-action arc.
- Do not add new story events, distract from the main action, over-animate quiet scenes, or force blinking into every shot.
- Do not place a blink, breath, or unrelated micro-motion on a critical fixed stare, exact contact, impact, or precision action.
- When micro-motion must be readable, specify its count, direction, timing, subject, intensity, and whether it repeats.
- For observational, conversational, and soft kinetic scenes, use motion only where visible and appropriate; total stillness remains valid when requested.

### Execution Precision Layer

- The video prompt must preserve reaction target relationships.
- If a reaction shot depends on a character, creature, vehicle, robot, prop, tool, device, object, or offscreen source, state the target clearly.
- When possible, keep part of the reaction target visible in the foreground, background, reflection, edge of frame, or spatial anchor.
- If the reaction target must remain offscreen, state the exact offscreen eye-line anchor.
- For small physical actions, mechanical struggle, object handling, procedural action, contact, resistance, or object state change, write a micro-action arc.
- A micro-action arc describes:

  1. Attempt.
  2. Resistance.
  3. Visible result.

- Do not exaggerate soft kinetic micro-action into violent impact unless the director requests it.
- Do not leave a physical struggle, mechanical struggle, or procedural action as a static object state if the beat requires attempted motion.

### Optional Keyframe Anchor Workflow

```yaml
  - single_global
  - cluster_anchors
  - per_shot_or_panel
```

Strategy definitions:

```text
none:

single_global:

cluster_anchors:

per_shot_or_panel:
```
